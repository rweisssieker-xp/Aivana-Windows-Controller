# Autostart im Store-Build

Die Store-Quellvariante blendet den bisher über den Benutzer-Run-Schlüssel verwalteten Autostart aus und weist Aufrufe zur Änderung zurück, bevor auf die Registry zugegriffen wird. Die normale Desktop-Variante behält das bisherige Verhalten. Damit wird für das erste Store-Paket keine nicht erprobte Autostart-Funktion angeboten. Die Auswahl der Varianten erfolgt über `StoreRelease` beim Build und ist nicht vom Überschreiben von Compilerkonstanten abhängig.

Die Änderung entfernt keine bereits von einer anderen Desktop-Installation gesetzten Autostart-Einträge. Die Konfiguration kann ein älteres Autostart-Feld behalten; die Store-Variante interpretiert dieses Feld nicht als Berechtigung zum Schreiben eines Run-Schlüssels.

Der bestehende Kandidat `artifacts/store-no-ai-20261028/MAKRIVO.msix` wurde **vor** dieser Änderung gebaut und enthält sie nicht. Vor Store-Einreichung einen neuen Kandidaten aus dem tatsächlich freigegebenen Quellstand erstellen, den genauen Hash dokumentieren und das Verhalten bei Installation, Start und Update unter Paketidentität auf einem geeigneten Testsystem prüfen. Bisherige Quell- und Pakettests ersetzen keine installierte MSIX-Prüfung oder WACK-Zertifizierung.

Der Store-Packager und Paketchecker verlangen einen in der Desktop-Assembly eingebetteten Store-Marker. Sie prüfen anhand von PE-Metadaten und IL, ohne die Assembly auszuführen, dass die Policy `false` meldet und abweist sowie `DesktopController.SetAutoStart` direkt abweist. Zudem verbieten sie bekannte schreibende Registry-API-Aufrufe in der Desktop-Assembly. Die Prüfung garantiert nicht, dass beliebiger Code nicht auf anderem Weg in die Registry schreibt; sie prüft auch nicht, ob die Benutzeroberfläche die Option tatsächlich ausblendet. Die Ausblendung muss beim installierten Paket explizit geprüft werden. Ein alter Retail-Kandidat ohne diese Sperre darf nicht erneut als aktuelles Store-Paket verpackt werden. Der technische Nachweis ist keine Signaturprüfung und kein Nachweis einer Windows-Installation. Der alte Kandidat wird von der neuen Prüfung bewusst abgewiesen; die frühere Integritätsprüfung bleibt eine historische Aussage über den damals verwendeten Checker.
